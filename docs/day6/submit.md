# 6일차 · 제출

!!! info "제출은 두 갈래 — 팀 저장소(공개)와 개인 비공개 폼"
    **팀**은 솔루션 킷을 공개 저장소의 릴리스 `v1.0` 링크 하나로 냅니다. **개인** 도입 기획서 · 나만의 KPI · ROI는 회사 이야기가 들어가므로 **비공개 폼으로만** 내고, 저장소에는 올리지 않습니다.
    폼 링크는 당일 강의장 화면과 이 페이지의 [강사 입력] 자리에 올라옵니다.

## 팀 제출 — 15:50 `v1.0` 릴리스 링크 {#team}

1. **15:40 코드 프리즈** — 이후로는 README와 릴리스 노트만 고칩니다.
2. README 5항목(목적 · 구성 · 실행 방법 · 데이터 출처와 가상 여부 · 담당자)과 [보안 점검](kit.md#security) 3검색(키 · 실명 · `@` → 0건)을 마칩니다.
3. 저장소 관리자: **Releases** → **Draft a new release** → 태그 `v1.0` → 릴리스 노트(P6-3 초안 → 사람이 고침) → **Publish release** → [릴리스 만들기](kit.md#release).
4. 릴리스 주소(`…/releases/tag/v1.0`)를 [팀 제출 폼 — 강사 입력]에 붙이고 제출합니다. 팀당 한 번이면 됩니다.
5. GitHub가 막히면 `d6_team_solution__T{조}.zip`(README 포함, 폴더 구조 그대로)으로 내고, 강사가 대신 올립니다.

- 15:50 이후에 고친 것은 `v1.1`로 새 릴리스를 만듭니다. 심사는 `v1.0` 기준입니다.
- 15:45에 발표 순서를 추첨합니다 → [7분 데모](kit.md#demo).

**개인 기획서 루브릭(각 1–4점)** — 서면 피드백과 최종본 확인에 같은 기준을 씁니다.

| 기준 | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 문제 정의 | 막연함 | 문제는 있으나 숫자 없음 | 숫자 기준선 있음 | 기준선 + 원인 가설 + 범위 |
| 데이터 준비도 | 원천 불명 | 원천만 적음 | 품질 · 가명처리 계획 | 샘플로 검증 완료 |
| 솔루션 적합성 | 도구 나열 | 파이프라인 일부 | 전 단계 + 사람 승인 | 전 단계 + 대안(Plan B) |

| 실행 가능성 | 계획 없음 | 로드맵만 | 30일 계획 | 30일 계획 + 승인 경로 |
